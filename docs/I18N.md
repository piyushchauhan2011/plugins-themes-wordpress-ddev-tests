# Internationalization and localization

Hotel Booking splits language work the same way WordPress does.

**Layer A — software strings (shipped).** Theme chrome and plugin UI use gettext. **Source catalogs** are `.pot` and `.po` in each `languages/` folder. Spanish (`es_ES`) is a working example. Compiled `.mo`, `.l10n.php`, and plugin editor `.json` are generated (`ddev compile-i18n`) and gitignored. `ddev compile-i18n` is still required for Layer A at runtime.

**Layer B — editorial content (Polylang copies).** Room titles, page copy, and menus are linked English/Spanish posts. Free Polylang is installed by `ddev seed-content` / `e2e/wp-env-seed.sh`, not committed (`.gitignore` already ignores other plugins). Inquiry rows stay in the guest’s own words. Do **not** add translation columns to `wp_hb_inquiries`.

```
Polylang URL (/ vs /es/)
  ├─ Layer A  theme hotel-booking-*.mo + plugin hotel-booking-core-*.mo
  │            labels, errors, pattern chrome, status labels
  └─ Layer B  linked hb_room, pages, wp_navigation copies
               wp_hb_inquiries rows stay in the guest’s own words
```

English stays unprefixed (`/rooms/`) via Polylang **hide default language**. Spanish is `/es/…`. Switching languages keeps gettext and content on the same locale.

## What we have today

| Piece | Layer | Where |
| --- | --- | --- |
| Theme UI | A | Text domain `hotel-booking`, [`load_theme_textdomain`](../wp-content/themes/hotel-booking/functions.php), [`languages/`](../wp-content/themes/hotel-booking/languages/) |
| Plugin UI | A | Text domain `hotel-booking-core`, [`load_plugin_textdomain`](../wp-content/plugins/hotel-booking-core/hotel-booking-core.php), [`languages/`](../wp-content/plugins/hotel-booking-core/languages/) |
| Inquiry status | A labels, B keys | Slugs `pending`, `contacted`, `closed` in MySQL; [`hotel_booking_inquiry_status_label()`](../wp-content/plugins/hotel-booking-core/inc/inquiries.php) for display |
| Rooms | B | Linked `hb_room` copies (Deluxe King ↔ King Deluxe). Numeric meta is copied, not translated |
| Inquiries | B (do not translate) | [`wp_hb_inquiries`](../wp-content/plugins/hotel-booking-core/inc/database.php) guest fields |
| Seed | B EN + ES | [`ddev seed-content`](../content/README.md) installs Polylang and copies |

## Layer A — gettext

Two domains, never mixed:

- Theme: `__( '…', 'hotel-booking' )`
- Plugin: `__( '…', 'hotel-booking-core' )`

HTML templates cannot call `__()`. User-facing chrome lives in PHP patterns (`patterns/404.php`, `footer-bar.php`, `rooms-archive.php`, …) that templates include with `<!-- wp:pattern -->`.

Interactivity view scripts must read strings from `wp_interactivity_state()` (see the color scheme toggle). Do not hardcode English in `view.ts`.

Editor scripts in the plugin use `@wordpress/i18n`. `wp_set_script_translations()` plus `wp i18n make-json` Jed files in the plugin `languages/` folder load Spanish in the block editor.

### Regenerating catalogs

```bash
ddev make-pot
```

That overwrites **`.pot` only**. Merge into hand-translated `.po` with `wp i18n update-po`, then compile (gitignored) binaries:

```bash
ddev compile-i18n
```

### Try Spanish locally

With Polylang active, the header **English / Español** links go to `/` and `/es/` (translated URLs). Polylang sets the locale from the URL, so Layer A `.mo` files and Layer B copies stay in sync. The cookie `hotel_booking_locale` / `?lang=` switcher is a **fallback** for PHPUnit and a site without the plugin.

Default site language stays English so Playwright specs keep matching **Send inquiry** unless a test clicks Español. Polylang **browser detection is off** so CI `Accept-Language` does not flip English specs.

You can still force wp-admin chrome with:

```bash
ddev wp language core install es_ES
ddev wp option update WPLANG es_ES
```

Core UI (wp-admin chrome, dates) comes from the WordPress.org language pack. Theme and plugin chrome come from the shipped `.mo` / `.l10n.php` files.

## Layer B — Polylang copies

| Content | Approach |
| --- | --- |
| `hb_room`, pages, menus | Free Polylang: one post per locale, linked. Not extra columns on `wp_posts`. |
| `hotel_name` setting | One brand string, or a translatable option later — not gettext. |
| Inquiry **rows** | Never duplicate. Name, email, message, dates are UGC. |
| Inquiry **status** | Keep English keys in SQL. Translate labels in Layer A. |
| `room_id` on an inquiry | The post ID the guest submitted. No table change. |
| REST / Stay grid | Filter rooms with `lang` (`pll_current_language()` or the REST argument). |

`hb_room` is registered on `pll_get_post_types`. When Polylang is missing (PHPUnit), cookie Layer A tests still pass and REST without `lang` still lists rooms.

Optional later: store the **guest UI locale** on the row (which language the form was in), not a translation of the message. Sketch only: [`snippets/inquiries-locale-column.php.example`](snippets/inquiries-locale-column.php.example). That is **not** in `dbDelta`.
